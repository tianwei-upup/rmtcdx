# 原生队列即时通知验收

日期：2026-10-23。本文记录专用阶段的即时通知、忙时排队、去重及荣耀刷新恢复。其后已完成未加载 / 审批补验并逐项目推广，当前范围见 [正文直入推广](NATIVE_DELIVERY_ROLLOUT.md)；下文“仅 acceptance”是当时的验收边界。

## 结论

发现当前已安装桌面支持 `codex://threads/wake/<threadId>`。与打开普通聊天 URL 不同，这条路由进入独立 wake 分支，不导航、不聚焦聊天、不携带提示词；桌面用已有 app-server 检查该会话的原生队列并 resume 原 ID。不需要桌面重启、MCP 热加载或第二执行器。

三条荣耀消息的原子接纳完成 → 原生 `task_started` 为 **877 / 316 / 423ms**；三个本机样本为 **258 / 180 / 246ms**。这些样本没有再等外部队列约十秒的检查周期。这里只证明本次专用样本，不承诺所有模型请求固定时延。

## 实现与安全边界

路径：手机业务意图 → 持久 Inbox → 原生 SQLite 原子追加并 fsync 回执 → **无正文 wake 提示** → 桌面已有原生队列执行 → 原生输出 / 完成投影。

- 保留原生 `queued_items` 原子 INSERT、唯一 client_id、完整 schema / migration 校验、prepared / accepted 回执和结果未知不重放。通知不再提交正文、不更换消息 ID、不覆盖整份队列。
- 新增 `native-queue-wake.mjs`，只允许专用 ID `01a13feb-ce80-7ca3-aa1e-17814542b353`，通知前重新检查归档 / cwd / 项目目录状态和本机唯一桌面进程。未向手机开放任意 URL 或 RPC。
- 固定核验当前安装 `app.asar` 内 bootstrap 和 main 两个路由相关 bundle 的 SHA-256；校验成功按文件身份及修改时间缓存，文件变化即重验。直入预检在原生写入前检查此条件。未知桌面源码禁止沿用该通知实现，不修改签名包。
- `open -g -a` 成功只记 `notification_dispatched`，不等于原生接纳、启动或完成。超时记 `notification_unknown`；不重插正文，保留原生周期检查兜底。Inbox 持久审计新增 `native.wake`，日志记录 intent / client_id / threadId / 通知起止时间，不含正文。
- 原生开始和完成继续按精确 client_id / turnId 对账。队列行消失不证明完成；恢复仍不重放已接纳正文。
- 未使用 follower start / steer / interrupt、旧整队列替换、伪造 owner 通知、原生 stdio 注入或共享 HOME 启动第二 app-server。

核对的当前桌面 CLI：`0.163.0-alpha.11.1`。当前安装源码中：

| 来源 | 实际行为 |
| --- | --- |
| bootstrap 的 threads/wake 路由 | 仅接受 UUID 路径，无 query / hash，进入 wake 集合；不放入导航队列 |
