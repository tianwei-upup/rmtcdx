## 实现

- Gradle `cloudUrl` 默认上述 ECS，空值可禁用；`windowsUrl` 直连构建仍可使用。首次没有连接配置时只写入默认 ECS 和 Mac，不覆盖自定义地址；旧 loopback 默认迁移仍有效。
- MCP 0.9.0 的 `executionMode` 来自本机用户批准的配置，默认 `readonly`，自用配置为 `desktop`。每次工具返回当前策略，已加载的新版前端可在不重启队列 worker 的情况下读取策略变化。手机请求体不能自行更改权限。
- MCP 工具说明与可信 Stop Hook 均按当前策略处理；有副作用步骤前及步骤之间检查取消。取消只停止后续操作，已有改动须如实报告，unknown 不重放。
- ECS desktop scope 另行声明 `executionMode` 和逐会话审批响应能力；云端只做消息与原生状态/审批投影，不成为执行器。
- `project-readonly` 仍是旧版精确项目目录授权的协议标签；当前执行能力由上述独立策略决定，不能再依据该旧标签判断手机只能只读。
- worker 启动核对会剥离 `/api/queue/config` 的展示能力字段，再验证精确目录 grant，修复新增桌面字段后冷启动核对失败的问题。

## 迁移中的问题与处理

1. 已加载的旧 MCP 不会因源文件更新而重载；旧进程仍返回只读工具说明。仅停止旧前端后会得到 `Transport closed`，不能靠杀进程完成热加载。
2. 当前 app 没有官方文档所写的 MCP servers 设置入口。用户虽已允许全局热加载，最终没有调用全局 reload；先对空闲的专用聊天做官方归档/恢复，验证原 ID 和历史保留、新 MCP 成功加载。随后对目标 RN 聊天先在无待办/无 inflight 时协作停止旧消费者，等待原生轮次结束，再归档/恢复并启用新轮次。未操作其他聊天。
3. 归档/恢复后，原历史观察者保留旧绑定，手机能收到任务结果却看不到新原生命令。仅重连对应的独立 observer 后，新历史恢复；复用原意图检查工具、结果与刷新，没有重放文件任务。这个维护路径须同时重新连接相应 observer。
4. RN ECS scope 更新时 Workbench 在 30 秒超时，没有返回成功正文；随后独立读回 service active、executionMode=desktop、14 个审批授权以及公网配置接口一致，确认更新已生效，没有盲目重跑部署。
