# 首段回复延迟定位与荣耀复验

日期：2026-10-23。最终配置下，原三条历史会话首轮首段为 29.2s / 20.1s / 19.9s；第二轮仍有 13.9–37.0s 波动。这是本轮样本，不是固定 SLA。

## 结论与改动

- 旧的 40–61 秒包含本机入队/原生启动、模型调用 listen、工具返回、模型生成公开答复、投影上传和手机显示，不能全部归因于模型。旧 dvr 本机首个 progress 在入队后 30.7 秒写入，捕获后到上传确认又等约 24.1 秒；ecs qq 分别为 32.6 秒和 10.7 秒；oisUpload 为 39.6 秒和 1.6 秒。旧记录没有手机时钟校准，不能把这些值与手机总时长直接相减当作精确阶段和。
- worker 18 秒 CPU 采样中，约 5.9 秒位于目录发现；共享 WAL 被其他活跃会话频繁更新时，即使查一个会话也会反复发现完整名单。现在在来源变化时查询精确会话，定期完整发现仍保留。每次读取当前归档/cwd；归属、删除、WAL 及桌面元数据变更立即失效，不使用时间 TTL 放宽权限。
- 目录发现原来重复解析约 3.3MiB 桌面状态。新增按 inode/大小/纳秒 mtime/ctime 区分的只读解析缓存，最多两个来源；发现前后仍验证项目/分配元数据一致。SQLite/WAL 改动仍新查询；desktopProjects 的原文件入口不变，发现流程复用已读的同一来源。
- 同条件交替十组只读基准：完整发现中位数 68.30→14.74ms；单会话查询 61.58→6.07ms。该测量说明本机发现开销下降，不能推断模型延迟同比下降。
- 新接入协议 v4：成功领取实际任务后，优先通过普通 commentary 给出有信息量的真实公开答复，原生流同步手机；不在领取前执行任务、不制造“收到/正在处理”等占位字符，较长内容继续 progress，最终仍以原租约 reply 完成。旧 v1/v2/v3 激活回执原文保持兼容，已经接纳的控制消息不改写、不重入队。模型未必每次都使用相同输出渠道；本轮 dvr/ois 的首段捕获到原生公开消息，ecs 的最早可见证据为队列进度。
- 新增本机控制接收/处理结束与 Inbox 分派时间日志，仅含操作、精确 ID 和时间，不记录租约/密码/正文。

## 手机链路观测

对 oisUpload 的实际队列 SSE，源 progress 提交→观测到达分别约 2.829s / 0.906s；服务器事件发出→观测到达约 2.800s / 0.879s。首段 progress 的 DOM 时间比经 USB 送到本机的 SSE 观测早约 12ms，说明事件收到后显示基本同步，而非前端再阻塞数秒。手机 JS 的另一次 18 秒采样约 93.1% 为 idle，只能代表该采样窗口。

剩余手机中继链路仍约秒级，未继续细分成公网、无线或 TCP 的具体原因；不得凭这些数据认定为某个网络设备故障。首段几十秒的大头已定位在原生回合和模型/工具往返。
