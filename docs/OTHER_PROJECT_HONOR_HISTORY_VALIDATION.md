## 发现的问题

### 1. 配置响应体超时绕过重试，登录仍有效却退到连接页

实际失败时，配置请求约 8 秒后中止，页面显示“暂时无法连接”；控制台记录 `queue_request_failed`、code `20`。同一登录态随后读取设备和配置均返回 200，排除了登录过期。成功配置响应约 517124 个字符；一次网络抓取确认 HTTP/1.1 chunked 传输。

`business/web/business-client.mjs` 的 `api()` 只把 `fetcher()` 放在网络错误捕获内，`response.json()` 位于外侧。响应头已返回、响应体因超时中止时，原始 `AbortError` / code 20 直接抛出。`catalog-live.mjs` 的 `loadCatalog()` 只重试 `network_unavailable`，因此此路径不会重试；`init().catch(failure)` 随后隐藏工作区并显示连接页。

正确调用层的隔离复现：请求阶段中止会尝试 3 次；响应体中止只尝试 1 次。“首次响应体中止、下一次成功”的只读 GET 用例当前断言失败。底层网络抖动的具体成因尚未穷尽；本轮已证明的是客户端恢复缺口，没有修改或扩大超时。

### 2. 完整文件历史切换到原生部分历史时，缺少保留与合并

`ScopedHistoryStream.attach()` 在 native state 到来后直接设置 `this.state=n.state`；`refresh()` 虽继续读取完整文件快照，但只在 `!this.native?.ready` 时应用快照。原生 canonical history 未完整加载时，可以用部分内容替换此前完整文件历史。

荣耀 `ecs qq` 实际出现 291 → 213 个原生展示项，`historyComplete=false` 持续超过 120 秒；第二轮后刷新才恢复完整。数据仍在原始历史中，不能把它描述成磁盘聊天被删除。`sleep`、`contextCompaction` 另被列为不支持的展示类型，不应把该列表与完整性标记混为同一原因。

使用真实 `ScopedHistoryStream.refresh()` 的隔离复现中，完整文件快照有 2 个 turn、已就绪 native 仅有 1 个 turn，refresh 后仍只有 1 个；保留完整前缀的断言当前失败。

### 3. 目录确认过期会中断发送，需要同 ID 重试

`oisUpload` 第二轮首次提交收到 `catalog_source_stale`，页面显示“电脑目录正在重新同步，请稍后发送”，本机 Inbox 当时没有该意图。`PersonalCatalog.fresh()` 要求最近一次确认小于 10000 毫秒；同阶段 worker 有 `network_unavailable` / code 23 日志，但尚不能据此确定所有确认间隔的成因。

观察到新一轮本机目录发布确认后，用 APK 的“重新发送”点击一次，保留 `2a7b7519-ae28-4751-8d04-544d5744deae`，随后自动接收并完成。保护没有被绕过，执行仍只有一次；目前存在需要用户干预的可用性空档，不能把本条记成首次发送无障碍通过。

## 测试脚本与产品结果的区分

- `dvr-demo` 初次测试观测包装错误地以对象方法调用原生 fetch，产生 `Illegal invocation`，请求未进入 ECS/Inbox。修正为 `Reflect.apply(..., window, ...)` 后，使用原意图重试；独立观察器保留了合法请求的两次中间结果。初始脚本错误及其总计时超时不计入产品时延或通过率。
- `oisUpload` 同 ID 重试产生两次 HTTP 尝试，触发了测试脚本“只能有一次 HTTP 提交”的断言。保留原失败记录，改按两个请求的意图、路由完全相同，以及本机审计只有一次入队/领取/完成，确认没有重复执行；未删除或篡改请求证据。
